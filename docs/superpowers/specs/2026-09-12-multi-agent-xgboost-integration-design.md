# XGBoost 与六智能体预警决策接入设计

## 目标

把算法组交付的六智能体状态机接入现有三端平台，并保持现有真实 CSV、XGBoost、登录权限和三端协同闭环不回退。演示主线必须能够清晰区分：算法预警、智能体研判、人工处置。

## 方案选择

采用 Node 运行时兼容层，不新增独立 Python 云服务。兼容层按照算法组 LangGraph 的节点、条件边和输出边界实现同构状态机，并在代码及界面注明来源。这样不改变 Vercel → Render → Supabase 的既有部署链路，也避免 Render 免费实例之间的双重冷启动。

未采用的方案：

- 独立部署原 FastAPI 服务：代码复用度最高，但需要增加第二个 Render 服务、跨服务鉴权、CORS、WebSocket 与持久化配置，演示风险较高。
- 浏览器端模拟动画：实现快，但不能形成可信的后端执行记录，不满足“接入智能体预警算法”的要求。

## 架构

```text
老师真实 CSV
  -> 既有离线预处理与 XGBoost 推理
  -> RoofRisk API 当前记录
  -> A1 感知预警（XGBoost 适配器，不使用 simulation-fusion-v1）
  -> A2 知识检索（既有真实相似案例）
  -> A3 调度决策（可审计候选方案）
  -> A5 资源评估（资源快照与缺口）
  -> A4 协同管控（仅生成待人工确认草案）
  -> A6 反思迭代（闭环或建议定向返回）
  -> 企业端 / 监管端 / 智库端
```

## 状态机

主路径保持算法组原顺序：A1 → A2 → A3 → A5 → A4 → A6。

- A1判定低风险时结束，不虚构后续处置。
- A1判定一般、较大或重大风险时继续知识检索。
- A5资源不可行时结束于资源缺口，不进入A4。
- A4输出为 `dry_run` 且状态为“等待人工确认”，不声称自动下发真实矿山控制指令。
- A6根据反馈输出闭环或返回A1/A3/A5/A4的建议；返回必须由操作人员确认。

## 后端接口

- `GET /api/multi-agent/status`：返回接入模式、节点版本和安全边界。
- `POST /api/multi-agent/run`：输入 `record_id` 及可选资源快照，使用既有仓库中的XGBoost记录执行六智能体状态机。
- `POST /api/multi-agent/reflect`：输入上次运行结果和现场反馈，只执行反思判断并返回人工确认建议。

接口沿用现有会话认证。运行结果包含 `workflow_run_id`、`warning_id`、`trace_id`、六节点状态、证据来源、耗时、当前阶段和下一动作。

## 前端呈现

在智库端科研分析大屏新增“算法预警 × 多智能体协同研判”板块：

- 顶部显示数据来源、XGBoost模型、记录号和风险等级。
- 中部显示六节点状态轨道，顺序为A1、A2、A3、A5、A4、A6。
- 下部显示当前选中Agent的输入证据、输出摘要、置信信息与安全边界。
- 点击“运行六智能体研判”才调用后端；不以纯前端计时动画冒充执行。
- 接口失败时明确显示“智能体服务不可用”，不回填伪造成功结果。

## 三端关系

六智能体是机器研判链，三端是人员业务链：

- 企业端接收A1预警与A4处置草案，完成现场处置和证据提交。
- 监管端核验企业执行结果，并向A6提供审批反馈。
- 智库端查看A2机理证据、A3方案、A6复盘和定向返回建议。

首期在智库端完整展示六智能体轨道，既有三端处置流程保持不变；后续只需将同一运行结果摘要分发到企业端和监管端，无需重写状态机。

## 真实性边界

- A1来源必须为 `teacher_real_csv_xgboost`，不得标记为算法组的规则阈值模型。
- A2相似案例来自既有真实数据记录；只能称“数据相似”，不能称“已证实的同类事故案例”。
- A3、A5、A4、A6属于规则辅助决策与演示性工作流，不代表生产级自动控制。
- 模型置信度、数据完整度和业务决策可信度分开显示。

## 验收标准

1. 较大/重大风险记录执行六个节点，顺序与算法组代码一致。
2. 低风险记录只执行A1，其余节点显示条件跳过。
3. 资源不足场景停在A5，A4和A6不执行。
4. A4始终等待人工确认且为dry-run。
5. API响应可追溯到真实记录号、XGBoost模型和数据哈希。
6. 智库端在Chrome常用宽度下无重叠，可清楚看到六节点状态和输出。
7. 既有自动化测试与离线提交预检继续通过。
